**Goal:** A working ticketing core — buy a ticket, get a QR, scan it once, and approve a cash sale — running locally against Postgres.

**Architecture:** One Next.js (App Router) app. Route handlers and server actions are the only writers; domain modules own transactions. Postgres is the source of truth. NocoDB is not in the write path for v1.

**Tech Stack:** Next.js 16, React 19, TypeScript strict, Drizzle ORM, Postgres 16 (Docker), Tailwind v4, zod, vitest.

**Spec:** `FRONTEND_PLAN.html` (§3 architecture, §5 API, §9 counter sales) + `PETCOM_PLATFORM_PLAN.md` §4/§5.

## Global Constraints

- Money is integer paise, names end `_paise`. Never floats.
- Times stored UTC (`timestamptz`), displayed IST.
- `qr_token` ≥ 128 bits of randomness, unique.
- Payment confirmation is server-side only; `markPaid` is idempotent.
- Inventory and check-in are single atomic statements (`UPDATE … WHERE … RETURNING`), never read-then-write.
- No secret reaches the browser. `DATABASE_URL` and keys are server-only.
- Cash/comp never mint a QR token; only an approver who is not the seller can issue.
- Every admin write lands in `audit_log`.

## Review Focus

- Two buyers on the last seat at the same millisecond — one wins, the other gets a clean "sold out".
- A webhook replayed three times — one order paid, one ticket set, one message job.
- Two scanners on one QR — one admits, one says "already used".
- A seller pasting their own approval URL — refused, not hidden.
- A pending cash sale abandoned for two hours — seats released, nobody stranded.
